# ADR 0003: Backend stack: FastAPI, SQLAlchemy async in Core, Alembic embedded, UUID v7, money in minor units

## Status

Accepted, 2026-09-26. Milestone 3 put the stack to work: the initial schema, the SQL adapters, the seller, session, product, restock, storefront and order routes, and the demo seed.

## Context

The requirements fix the backend: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 in async mode, Alembic and PostgreSQL 16, with no SQL built by hand. The hot path is short and must be explicit: a comment becomes a handful of statements (settle the comment, reserve the stock, record the intent, open the order), and their exact shape is what prevents overselling (ADR 0005). The API publishes an OpenAPI contract from which the TypeScript client is generated, and the layered architecture (ADR 0002) keeps the framework and the database out of the domain. Amounts are summed and multiplied, and read by JavaScript clients.

## Decision

### FastAPI, served by uvicorn

- FastAPI 0.141.1 on Starlette 1.7.0, served by uvicorn[standard] 0.54.0: one process per container (`uvicorn livecart_api.main:app`), scaled by running more containers. `livecart_api.main` is the composition root: it validates the settings, configures the JSON logs and calls `create_app(settings, build_resources(settings))`. The app factory receives every adapter through `Resources`, so the unit tests build the same app around the in-memory fakes and the integration tests around the SQL adapters on `livecart_test`.
- Request bodies are Pydantic 2.13.5 models with `extra="forbid"` and a bound on every field; answers are response models of their own, never the records of the repositories. The errors of the ports and the domain answer from one table (`livecart_api.errors`) with fixed messages.
- The OpenAPI schema is `app.openapi()`, written deterministically to `packages/api-client/openapi.json` by `services/api/scripts/export_openapi.py`, with the handler names as operation ids; CI fails when the committed file differs from what the code produces. `/docs` and `/openapi.json` are served in development only.
- pydantic-settings 2.15.0 reads the environment, then `.env`: `Settings` validates everything when a process starts, and every secret, connection URLs included, is a `SecretStr`.

### SQLAlchemy 2 async, Core only

- SQLAlchemy 2.0.54 with asyncpg 0.31.0, and no ORM: `livecart_core.infrastructure.db.tables` describes every table as Core metadata, and the adapters build every statement from Core constructs (`select()`, `insert()`, `update().where().returning()`), then map rows to the frozen records of `application.dto` by hand. An architecture test refuses `sqlalchemy.text`, `literal_column` and `TextClause` in every runtime module of `livecart_core`, beside ruff's `S608` everywhere; `infra/postgres/*.sql` is the only SQL written by hand, besides the DDL of the migrations.
- One `AsyncEngine` per process: READ COMMITTED pinned, `statement_timeout` 5000 ms and `lock_timeout` 2000 ms set on the server side, `pool_pre_ping`, and `hide_parameters` so that bound values never reach an error message. The API's pool holds 5 connections plus 10 on overflow (`API_POOL`); `WORKER_POOL`, 20 plus 2, sizes the worker's, and the concurrency test of ADR 0005 runs through it.
- A repository method is one transaction (`units.transaction`): lock and statement timeouts, deadlocks, serialization failures and lost or refused connections come out as `ServiceUnavailable`, every other error keeps its type.

### Alembic, embedded in the package

- Alembic 1.20.0, with its revisions inside `livecart_core` (`script_location = "livecart_core:migrations"`), run by `livecart-migrate`, which needs no `alembic.ini` and takes its URL from `MIGRATOR_URL`. The one-shot `migrate` container runs `upgrade head` as `livecart_migrator` before the API and the worker start; the runtime role cannot alter the schema.
- The revisions are written by hand and never import the metadata, so each one keeps building the schema of its day. An integration test builds the metadata in a scratch schema and compares PostgreSQL's own description of both (columns, constraints, indexes); another runs every revision up, down and up again.

### Identifiers, amounts, times and closed lists

- Primary keys are UUID v7, generated by the application with uuid-utils 1.0.0 (`ids.new_id`), since neither PostgreSQL 16 nor the Python 3.12 standard library has them. They sort by creation time: lists are keyset pages on the id, and the B-tree of each key grows at its right edge. The id is known before the insert, so the order's token hash is computed with it (ADR 0007).
- Money is `Money(amount_minor: int, currency)`: integer minor units, never a float or a `Decimal`, in `BIGINT` columns checked `>= 0`. The currency is `CHAR(3)`, frozen on each order, and `DEFAULT_CURRENCY` (EUR) is the one currency of a deployment. A price is at most 100,000,000 minor units, so that a total of 99 units stays below 2^53, the largest integer a JavaScript client reads exactly.
- Timestamps are `timestamptz`. Every time a use case decides with (a deadline, a lease, a start) comes from the `Clock` port; the database clock only fills the `created_at` of rows written without one, and every `updated_at`.
- Closed lists are `VARCHAR` columns with a named `CHECK` built from the enum of the code; every constraint and index carries an explicit name, the plan's where it gives one, so that an adapter can tell which one refused a row.

## Consequences

- The SQL of the hot path reads in the adapters as it runs, and an integrity error names its constraint: `uq_orders_pending_buyer_product` and `uq_orders_reference` are told apart by name (ADR 0005, ADR 0007).
- Without an ORM there is no lazy loading, identity map or implicit flush, and rows are mapped to records by small functions written by hand.
- A schema change is two edits, the revision and the metadata, and CI fails when they differ.
- Migrations ship in the image of the code that uses them, and run once per deployment, before any process that uses the schema.
- Amounts are exact everywhere, and the clients format them from the minor units and the currency.
- SQLAlchemy stays on 2.0.54, the version pinned in `packages/livecart-core/pyproject.toml`.

## Alternatives considered

- **The SQLAlchemy ORM**: sessions and implicit queries around a hot path of a few explicit statements whose exact shape matters.
- **asyncpg with SQL strings**: no metadata to compare the migrations with, and SQL written by hand, which the requirements forbid.
- **Django and its ORM, or Litestar**: Django's ORM and request stack are synchronous at heart; Litestar has a smaller ecosystem than FastAPI, which the requirements name.
- **Migrations at API startup**: every replica would race to run them, and the runtime role would need to alter the schema.
- **UUID v4 or `bigserial` keys**: v4 ids insert at random places in the index and do not sort by time; a sequence needs a privilege for the runtime role, allocates the id only at insert and makes ids guessable.
- **`Decimal` or float amounts**: floats round; decimals need care at every boundary, JSON included, where integers of minor units need none.
