# Security policy

LiveCart is a personal demo project with a fictional brand. It has no production deployment ([docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) is designed, not executed), and its payments run in Stripe's test mode only. This document says how to report a vulnerability, then records the security review of the code as it stands: the OWASP API Security Top 10 (2023), the inventory of the endpoints, the retention of data and the known limits. Claims name the code or the test they rest on.

## Reporting a vulnerability

- **Report privately**, through GitHub's private vulnerability reporting: the repository's **Security** tab, then **Report a vulnerability**. The report stays visible to the maintainer only until an advisory is published.
- **Never in public**: no issue, pull request, discussion or comment that describes the vulnerability. If the **Report a vulnerability** button is missing, open an issue that asks for a private channel and says nothing else about the problem. No e-mail address is published for reports.
- **What helps**: the commit you tested, the component (API, worker, dashboard, buyer app, compose or images), the steps to reproduce on the local stack (`docker compose up`), and what an attacker gains.
- **Scope**: the code and configuration of this repository. Out of scope: the services LiveCart calls (Stripe, Anthropic), the `change-me` placeholders of `.env.example`, which every process refuses when `APP_ENV=production`, and attacks that need control of the developer's machine. Test against your own local stack only.
- **Versions**: only `main` is maintained; there are no releases. One person maintains the project, so reports are answered on a best-effort basis; a fix lands on `main`, then the advisory is published.

## Endpoint inventory

Every route of the API (`services/api/src/livecart_api/routes/`), as `create_app` mounts them (`livecart_api.app`): 27 in production, 33 in development with the mock payment provider. The committed `packages/api-client/openapi.json` is exported in production mode and documents 26 of them, all but the HTML bridge page; CI fails when it drifts from the code (`openapi-drift` job, `scripts/check-openapi-drift.mjs`), and `test_the_table_holds_every_seller_route_that_names_an_object` fails when a seller route escapes the cross-seller test.

**On every route**, first: a `Host` outside `ALLOWED_HOSTS` gets 400 (`TrustedHostMiddleware`), a body over 1 MiB gets 413 (`RequestBodyLimitMiddleware`, and `client_max_body_size 1m` in nginx; `test_a_body_over_1_mib_is_refused_whether_announced_or_streamed`), and every answer carries the security headers of `livecart_api.middleware.security_headers`.

**Authentication**, as the table names it:

- **seller**: `Authorization: Bearer <access token>`, a JWT checked by `CurrentSeller` (`livecart_api.deps`, `livecart_api.access_tokens`): HS256 only, `iss`, `aud`, `sub`, `exp` and `jti` required, 15 minutes. Another seller's object answers 404, like an unknown id.
- **order token**: `Authorization: Bearer <order token>`, compared in constant time with the order's stored hash (`LookUpOrder.with_token`, `livecart_core.order_tokens`). A missing or wrong token answers the 404 of an unknown reference, never 401.
- **cookie + Origin**: the HttpOnly `lc_refresh` cookie (`SameSite=Strict`, `Path=/api/v1/auth`, `Secure` in production), and an `Origin` header naming the API's own origin, 403 otherwise (`require_same_origin`).
- **signature**: an HMAC, or the provider's signature, over the raw body, checked before the body is parsed.

**Rate limits**: fixed windows counted in Redis (`livecart_core.infrastructure.ratelimit`; rules in `livecart_api.rate_limits`), 429 with `Retry-After`. A client address is the one uvicorn takes from `X-Forwarded-For` as nginx overwrites it, IPv4 as is and IPv6 by its /64 (`test_ipv4_addresses_count_alone_and_ipv6_ones_by_their_slash_64`). While Redis is down, the two login rules fail closed (503) and every other rule lets requests through and counts the failure (`test_without_the_counters_logins_close_and_the_refresh_stays_open`, `test_without_the_counters_other_routes_pass_and_the_failure_is_counted`). The numbers are the defaults of `livecart_core.settings`, each changed by a `RATE_LIMIT_*` variable.

## Retention policy

What LiveCart keeps, where, and for how long, as the code stands. **No code purges, anonymises or expires personal data in PostgreSQL**: the runtime role `livecart_app` has SELECT, INSERT and UPDATE and never DELETE (`infra/postgres/grants.sql`, `test_the_runtime_role_reads_and_writes_every_table_but_never_deletes`), so every row lives until someone deletes it as the migrator. The only code that does is `livecart-seed --reset-loadtest`, which empties the load-test session's comments, intents, orders, payments and shipments before a k6 run (`livecart_core.infrastructure.db.session_reset`). A purge job running as the migrator is on the roadmap (ADR 0004, ADR 0011); until it exists, the retention of PostgreSQL is "kept".

What never reaches LiveCart, or never leaves it:

- **Cards**: the buyer pays on Stripe's hosted page. LiveCart sends the amount, a product name and three metadata fields (order id, attempt, reference), and reads back the session's id, URL, status, amount, currency and payment intent (`livecart_core.infrastructure.payments.stripe`). The raw webhook body, which carries the customer's details, is reduced to the allow-list before anything is stored (`test_payment_webhook.py`, `test_stripe_payments.py`).
- **Secrets and tokens in logs**: keys whose name ends in `password`, `secret`, `token`, `authorization`, `cookie` or `api_key` are redacted, and CR and LF are escaped (`livecart_core.logging`, `test_sensitive_values_are_redacted`, `test_line_breaks_cannot_forge_log_lines`). Redaction looks at the top-level keys of a log event only, not at nested values nor at the message, so the guarantee rests on not passing such values in the first place: `test_the_buyer_gets_the_derived_token_on_the_dev_stream_and_no_log_holds_it` runs the worker at DEBUG, SQL statements included, and finds no order token in any line. SQLAlchemy runs with `hide_parameters=True`.
- **The LLM**: with `ANTHROPIC_API_KEY` set, the worker sends an ambiguous comment's text and the session's catalog, never the author's identity nor an address (`livecart_worker.llm.claude`).

## Known limits

What the measures above do not cover, as the code stands. Most are decisions recorded in the ADR named, with their fix on the roadmap; the others come from this review.

### Authentication and keys

- **The 30 s refresh grace** (ADR 0010). A refresh token reused within 30 s, while its successor is still active, gets an access token without a new cookie: tabs that race on one refresh stay signed in. A stolen refresh token used inside that window obtains access tokens, never a refresh token; after it, a replay revokes the family.
- **HS256 with one key, no rotation** (ADR 0010). `JWT_SECRET` signs every access token; changing it invalidates all of them at once, while the refresh cookies, stored as hashes independent of it, go on issuing new ones. An access token cannot be revoked during its 15 minutes, a logout included: logging out revokes the refresh family, and the other tabs keep their access token until it expires (ADR 0017).
- **One `ORDER_TOKEN_KEY`** (ADR 0007). Whoever holds it can compute every order's token, and its rotation is not implemented; a single order's token cannot be revoked either, since it is derived rather than stored. A database leak alone gives no usable token: only hashes are stored.
- **A script injected in the dashboard** could use the access token while the page is open, though it can read neither the refresh token nor a stored copy (ADR 0010, ADR 0017): hence the strict CSP of the SPA, with no inline script and no `eval`.

### Limits and abuse

- **Fixed windows let bursts through** (ADR 0011). A fixed window lets up to twice a limit through around its edge; a sliding window is not implemented.
- **A Redis outage** closes the logins (503) and opens every other limit, which then counts nothing (ADR 0011); the not-found warning across addresses goes silent with it.
- **The public lookup by reference** shows an order's status and total: a reference has about 2^30 values and is read aloud on a live, and an address finds nothing for up to a minute after 20 not-found answers, existing orders included (ADR 0007). A whole audience behind one mobile carrier's address shares those windows.
- **The LLM budget can be overshot** (ADR 0006). The day's spend is checked before a call and known after it, so the calls in flight when the budget is reached go through: up to 4 per worker process, about $0.12 past `LLM_DAILY_BUDGET_USD` per worker with `claude-opus-5`, $0.36 with three workers. Reserving each call's worst case first is on the roadmap with per-seller limits.

### Network and exposure

- **Metrics are protected by the network only** (ADR 0014). Port 9100 of the API and the worker has no authentication: any container of the compose network can read it, and prometheus-client answers any path there with the metrics. They are never published on the host and never routed by nginx; no scraper runs yet.
- **Port 8080 is open on the LAN in development** (ADR 0011), so that a phone running Expo Go reaches nginx; the API's own port is published on `127.0.0.1` only.
- **Custom URL schemes can be intercepted** (plan, Universal Links on the roadmap). The buyer's link is `<scheme>://link/<reference>#t=<token>`: another app that registers the same scheme on the phone can receive it, and the token with it. The token stays out of every URL sent to a server, in the fragment only.
- **The comment webhook trusts its key.** The `simulator` adapter, the signed common format, stays served in production while it is enabled: whoever holds `COMMENT_WEBHOOK_SECRET_SIMULATOR` can post comments, under any author, to any live session of that platform. The platform adapters are stubs.

### Data

- **Comment text is kept without purge** (ADR 0004, ADR 0011). The inbox keeps every comment's text and author, the orders keep their shipping addresses, and nothing deletes or clears them; the runtime role cannot delete at all, and a purge job running as the migrator is on the roadmap. See [Retention policy](#retention-policy).
- **No log retention is configured**, and uvicorn's access lines hold the client's address and the paths, which name order references.
- **Redaction looks at top-level log keys only**: a credential nested in a structure or written into a message would not be masked. The tests check that order tokens, tracking numbers and passwords reach no log line; no test checks shipping addresses.

### Payments and deployment

- **The Stripe adapter is tested offline only** (ADR 0008). Its contract tests run the real SDK against `FakeStripeApi`, an in-memory stand-in of the three Checkout Session calls; no test reaches api.stripe.com, and none has run against a real Stripe test account. Live keys are refused.
- **No production deployment exists**, and none can start as the code stands: the worker refuses `APP_ENV=production`, its only buyer notifier writing order tokens to a development stream (ADR 0007, [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)). The deployment design adds its own limits, listed there: the migrator's URL in the API's environment for the pre-deploy command, and a second trusted hop in front of nginx.
- **Supply chain**: a newly published advisory turns CI red without any change, by design; Dependabot is not configured yet, and the Trivy filesystem scan does not read `uv.lock`, which pip-audit and the image scan cover (ADR 0015). The PostgreSQL and Redis containers keep their images' entrypoints, which need `chown`, so they run without `read_only` or `cap_drop`.
